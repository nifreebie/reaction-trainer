## 1) Постановка задачи и описание проекта

Цель проекта Reaction Trainer - разработать аппаратно-программный тренажер реакции, который позволяет игроку проходить серию раундов на физическом устройстве, измерять время реакции и сохранять результаты на сервере. Система объединяет микроконтроллерное устройство на базе NodeMCU ESP8266 и backend-приложение на Spring Boot.

Основная задача тренажера состоит в том, чтобы после случайной задержки показать игроку целевую кнопку, зафиксировать нажатие и определить результат раунда. В зависимости от поведения игрока раунд может завершиться успешным нажатием, ошибкой выбора кнопки, пропуском или фальстартом. По итогам игры сервер рассчитывает среднее время реакции, лучший результат, количество промахов, неправильных нажатий и фальстартов.

Проект решает несколько прикладных задач:

- регистрация игроков и авторизация через JWT;
- регистрация физических устройств и выдача device token;
- сопряжение игрока и устройства через шестизначный код;
- обмен сообщениями между устройством и сервером через WebSocket;
- проведение игровой сессии из заданного количества раундов;
- сохранение истории сессий, результатов и статистики в PostgreSQL;
- предоставление REST API для управления игроками, устройствами, сессиями и лидербордом.

В результате получается система, которую можно использовать как учебный пример IoT-проекта: есть аппаратная часть, прошивка, сетевой протокол, backend, база данных и API-документация.

## 2) Общая архитектура системы

Система построена по клиент-серверной архитектуре. В роли аппаратного клиента выступает плата NodeMCU ESP8266 с подключенными устройствами ввода и вывода. Серверная часть реализована на Java 17 и Spring Boot 4. Для хранения данных используется PostgreSQL. В проекте также присутствует OpenAPI-описание REST API и Docker Compose-конфигурация для локального запуска базы данных.

Основные компоненты системы:

- аппаратное устройство: NodeMCU ESP8266, клавиатура для ввода кода, панель с кнопками и светодиодами, дисплей, buzzer;
- прошивка: Arduino/C++ код, который управляет вводом, индикацией, звуком, Wi-Fi и WebSocket-соединением;
- backend: Spring Boot-приложение, реализующее REST API, WebSocket endpoint, бизнес-логику игры и работу с БД;
- база данных: PostgreSQL для хранения игроков, устройств, кодов сопряжения, сессий, раундов и результатов;
- API-клиент или веб-интерфейс: внешний пользовательский слой, который работает с REST API для регистрации, входа, создания pair-code и просмотра результатов.

Упрощенный поток работы выглядит так:

1. Игрок регистрируется или входит в систему через REST API.
2. Физическое устройство регистрируется на сервере и получает токен.
3. Устройство подключается к Wi-Fi и открывает WebSocket-соединение с сервером.
4. Игрок создает код сопряжения.
5. Код вводится на клавиатуре устройства.
6. Сервер связывает игрока и устройство, создает игровую сессию и запускает игру.
7. Устройство получает команды раундов, показывает стимулы и отправляет результаты.
8. Backend сохраняет данные, считает статистику и отправляет сообщение о завершении игры.

Такое разделение позволяет независимо развивать серверную часть, прошивку и клиентский интерфейс.

## 3) Аппаратная часть

Аппаратная часть проекта рассчитана на NodeMCU v3 Lolin на базе ESP8266. Эта плата выбрана из-за встроенного Wi-Fi, поддержки Arduino IDE и достаточного количества GPIO для подключения внешних модулей.

Используемые компоненты:

- NodeMCU v3 Lolin / ESP8266;
- клавиатура 4x3 для ввода шестизначного кода сопряжения;
- I2C-расширитель PCF8574 для подключения клавиатуры;
- TM1638-подобная панель с 8 кнопками, 8 LED и 7-сегментным дисплеем;
- buzzer для коротких звуковых сигналов и финальной мелодии;
- питание для платы и периферийных модулей.

Назначение пинов в прошивке:

| Назначение | NodeMCU pin | GPIO |
| --- | --- | --- |
| I2C SDA | D2 | GPIO4 |
| I2C SCL | D3 | GPIO0 |
| Buzzer | D1 | GPIO5 |
| TM STB | D5 | GPIO14 |
| TM CLK | D6 | GPIO12 |
| TM DIO | D7 | GPIO13 |

Клавиатура подключается через PCF8574 по I2C. По умолчанию используется адрес `0x20`. Раскладка клавиатуры:

```text
1 2 3
4 5 6
7 8 9
* 0 #
```

Клавиша `*` очищает введенный код, а клавиша `#` отправляет код на backend. Основная игровая панель используется уже во время раундов: сервер отправляет номер целевой кнопки от 1 до 8, устройство включает соответствующий LED и ожидает нажатие.

## 4) Программная архитектура

Backend реализован как Spring Boot-приложение с классическим разделением на слои:

- `controller` - REST-контроллеры для авторизации, игроков, устройств, кодов сопряжения, сессий и результатов;
- `service` и `service.impl` - бизнес-логика приложения;
- `repository` - Spring Data JPA-репозитории для доступа к данным;
- `domain` - JPA-сущности предметной области;
- `dto` - объекты запросов, ответов и WebSocket-сообщений;
- `config` - настройки безопасности, WebSocket, CORS, JSON и игровых параметров;
- `util` - вспомогательные классы, JWT-фильтр, обработчик WebSocket и исключения.

Ключевые доменные сущности:

- `Player` - пользователь системы;
- `Device` - зарегистрированное физическое устройство;
- `PairCode` - временный код сопряжения игрока и устройства;
- `GameSession` - игровая сессия;
- `ReactionRound` - отдельный раунд реакции;
- `Result` - сохраненный результат игрока.

Для авторизации игроков используется Spring Security и JWT. Пароли хранятся в зашифрованном виде с помощью BCrypt. Большинство REST endpoint защищены JWT, кроме регистрации/входа и регистрации устройства. Устройство подключается к WebSocket endpoint `/ws/devices` с параметрами `deviceId` и `token`; проверка выполняется на этапе handshake.

Игровые настройки вынесены в `application.yaml`:

```yaml
app:
  game:
    rounds-count: 10
    timeout-ms: 1500
    target-buttons-count: 8
    stimulus-delay-min-ms: 500
    stimulus-delay-max-ms: 2000
```

За игровой процесс отвечает `GameFlowServiceImpl`. Сервис запускает сессию, создает раунды, выбирает случайную целевую кнопку, отправляет команды устройству, принимает результаты и обновляет статистику. Сопряжение реализовано в `PairingServiceImpl`: сервер проверяет код, online-статус устройства, связывает устройство с игроком и создает сессию в статусе `WAITING`.

Прошивка написана на Arduino/C++ и содержит собственную машину состояний:

- `ENTER_PAIR_CODE` - ввод кода сопряжения;
- `WAIT_PAIRING` - ожидание ответа сервера;
- `COUNTDOWN` - обратный отсчет перед игрой;
- `WAIT_ROUND` - ожидание следующего раунда;
- `ROUND_PAUSE` - пауза между раундами;
- `WAIT_STIMULUS` - ожидание появления стимула;
- `WAIT_PRESS` - ожидание нажатия кнопки;
- `GAME_FINISHED` - отображение результата и ожидание сброса.

## 5) Функциональные возможности системы

Система предоставляет полный цикл работы с тренажером реакции: от регистрации игрока и устройства до прохождения игры и анализа результатов.

Основные возможности:

- регистрация и вход игрока;
- получение JWT-токена для защищенных API-запросов;
- регистрация устройства с выдачей device token;
- подключение устройства к серверу по WebSocket;
- создание и проверка активного pair-code;
- ввод кода на физической клавиатуре;
- автоматический старт игровой сессии после успешного сопряжения;
- проведение игры из 10 раундов по умолчанию;
- случайный выбор целевой кнопки и задержки стимула;
- обработка успешных нажатий, ошибок, пропусков и фальстартов;
- расчет среднего и лучшего времени реакции;
- хранение истории сессий и результатов;
- просмотр статистики игрока и лидерборда.

### 5.1 Пользовательский интерфейс

В текущем проекте пользовательский интерфейс представлен двумя уровнями: физическим интерфейсом устройства и программным REST API, на основе которого может быть построен веб-интерфейс.

Физический интерфейс включает:

- клавиатуру 4x3 для ввода кода сопряжения;
- 7-сегментный дисплей для отображения введенного кода, обратного отсчета, номера целевой кнопки и итогового результата;
- LED-индикацию целевой кнопки на игровой панели;
- кнопки игровой панели для реакции игрока;
- звуковые сигналы buzzer для обратной связи.

С точки зрения игрока сценарий прост: получить код в клиентском интерфейсе, ввести его на устройстве, дождаться обратного отсчета, нажимать подсвеченные кнопки и после завершения увидеть итоговое среднее время реакции.

REST API выполняет роль интерфейса для веб-клиента или мобильного приложения. Через него можно регистрироваться, входить в систему, создавать коды сопряжения, смотреть активную сессию, историю игр, статистику и таблицу лидеров.

### 5.2 Игровая логика

Игровая логика строится вокруг сессии и раундов. После успешного сопряжения backend создает `GameSession`, переводит ее в активный статус и отправляет устройству первый `round_start`.

Для каждого раунда сервер:

1. выбирает случайную целевую кнопку в диапазоне от 1 до 8;
2. выбирает случайную задержку появления стимула;
3. сохраняет раунд в базе данных;
4. отправляет устройству WebSocket-сообщение с номером раунда, целевой кнопкой, задержкой и timeout.

Устройство после получения раунда показывает стимул, включает LED и измеряет время от появления стимула до нажатия. Возможные результаты:

- `HIT` - игрок нажал правильную кнопку вовремя;
- `WRONG_BUTTON` - игрок нажал неправильную кнопку;
- `MISS` - игрок не нажал кнопку за отведенное время;
- `FALSE_START` - игрок нажал кнопку до появления стимула.

Backend дополнительно нормализует результат. Если устройство отправило некорректные данные, сервер проверяет timeout, номер целевой кнопки и наличие времени реакции. Это повышает надежность системы, так как итоговый результат не зависит только от прошивки.

После последнего раунда сессия переводится в статус `FINISHED`, сохраняется лучший результат игрока, а на устройство отправляется сообщение `game_finished`.

### 5.3 Работа с сетью (Wi-Fi)

Wi-Fi используется для подключения NodeMCU ESP8266 к локальной сети, в которой доступен backend. В прошивке задаются:

```cpp
const char* WIFI_SSID = "YOUR_WIFI";
const char* WIFI_PASSWORD = "YOUR_WIFI_PASSWORD";
const char* BACKEND_HOST = "192.168.1.10";
const uint16_t BACKEND_PORT = 8080;
```

После включения устройство работает в режиме `WIFI_STA`, подключается к заданной сети и выводит IP-адрес в Serial Monitor. Затем прошивка открывает WebSocket-соединение:

```text
ws://BACKEND_HOST:8080/ws/devices?deviceId=nodemcu-01&token=DEVICE_TOKEN
```

Для поддержания online-статуса устройство отправляет heartbeat каждые 5 секунд. На сервере настроен timeout heartbeat: если сообщения долго не приходят, устройство считается offline. По умолчанию timeout равен 20 секундам, а проверка offline-статуса выполняется периодически.

При разрыве WebSocket-соединения прошивка возвращается к состоянию ввода кода, а библиотека WebSockets пытается переподключиться с интервалом 3 секунды.

### 5.4 Взаимодействие с сервером и веб-интерфейсы

Взаимодействие с сервером делится на REST API и WebSocket-протокол.

REST API используется игроком или веб-интерфейсом. Основные endpoint:

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| POST | `/api/auth/register` | регистрация игрока |
| POST | `/api/auth/login` | вход игрока |
| GET | `/api/me` | получение данных текущего игрока |
| POST | `/api/devices/register` | регистрация устройства |
| GET | `/api/devices/me` | список устройств игрока |
| POST | `/api/pair-codes` | создание кода сопряжения |
| GET | `/api/pair-codes/active` | активный код сопряжения |
| GET | `/api/sessions/current` | текущая сессия |
| GET | `/api/sessions/me` | история сессий |
| GET | `/api/sessions/{id}/rounds` | раунды сессии |
| GET | `/api/results/leaders` | таблица лидеров |
| GET | `/api/results/me/best` | лучший результат игрока |

WebSocket используется физическим устройством. Сообщения от устройства:

```json
{"type":"heartbeat"}
{"type":"pair_request","code":"123456"}
{"type":"round_result","sessionId":"uuid","roundNumber":1,"pressedButton":2,"reactionTimeMs":350,"result":"HIT"}
```

Сообщения от backend:

```json
{"type":"connected","deviceId":"nodemcu-01"}
{"type":"pair_success","sessionId":"uuid","playerName":"player1"}
{"type":"round_start","sessionId":"uuid","roundNumber":1,"targetButton":2,"stimulusDelayMs":800,"timeoutMs":1500}
{"type":"game_finished","sessionId":"uuid","avgReactionMs":360,"bestReactionMs":280,"missesCount":1,"wrongButtonsCount":0,"falseStartsCount":0}
{"type":"error","message":"Invalid or expired code"}
```

Такой подход удобен: REST API подходит для обычных пользовательских действий, а WebSocket обеспечивает быстрый двусторонний обмен с устройством во время игры.

## 6) Эксплуатация и оптимизация

Для локальной эксплуатации требуются JDK 17, Maven, Docker и Docker Compose. База данных PostgreSQL запускается через `compose.yaml`. Backend читает параметры подключения из `.env`:

```dotenv
POSTGRES_USER=nifreebie
POSTGRES_PASSWORD=nis150905
POSTGRES_URL=jdbc:postgresql://localhost:5432/reaction_trainer_db
```

Типичный запуск:

```bash
docker compose up -d
mvn spring-boot:run
```

После запуска backend доступен на `http://localhost:8080`. Прошивку необходимо открыть в Arduino IDE, указать Wi-Fi, IP backend, `DEVICE_ID` и `DEVICE_TOKEN`, затем загрузить на NodeMCU.

Оптимизация в проекте уже частично заложена:

- коды сопряжения заранее генерируются в пуле, что снижает задержку при запросе нового кода;
- устаревшие и использованные коды периодически удаляются;
- online-статус устройства контролируется через heartbeat;
- WebSocket-сессии устройств хранятся в отдельном registry;
- игровая логика на сервере проверяет и нормализует результаты;
- настройки игры вынесены в конфигурационный файл без необходимости менять код.

Для проверки backend предусмотрена команда:

```bash
mvn test
```

Тестовый профиль использует H2 in-memory database, что упрощает запуск тестов без внешней PostgreSQL.

## 7) Ограничения и развитие

Текущая версия проекта решает основную задачу, но имеет ряд ограничений:

- веб-интерфейс как отдельное frontend-приложение в репозитории отсутствует, взаимодействие выполняется через REST API;
- прошивка рассчитана на конкретную схему подключения и конкретные модули;
- WebSocket endpoint разрешает все origins, что удобно для разработки, но требует уточнения для production;
- секрет JWT в `application.yaml` задан статически и должен быть вынесен в переменные окружения для реального развертывания;
- device token отображается только при регистрации устройства, поэтому при его потере требуется повторная регистрация или механизм перевыпуска;
- игровой режим пока фактически один - `CLASSIC`;
- точность измерения зависит от аппаратной реализации, качества кнопок, задержек Wi-Fi и обработки цикла прошивки.

Возможные направления развития:

- разработать полноценный веб-интерфейс для игроков и администратора;
- добавить разные режимы игры: тренировка точности, быстрый старт, дуэль, марафон;
- добавить настройку количества раундов и timeout для конкретной сессии;
- реализовать OTA-обновление прошивки;
- добавить графики прогресса игрока;
- добавить управление несколькими устройствами и комнатами;
- улучшить безопасность WebSocket и хранение секретов;
- добавить интеграционные тесты WebSocket-протокола;
- сделать корпус устройства и схему подключения в виде отдельной документации.

## 8) Заключение и вывод

Проект Reaction Trainer представляет собой завершенный пример аппаратно-программной системы для тренировки реакции. В нем объединены физическое устройство на ESP8266, прошивка на Arduino/C++, сервер на Spring Boot, база данных PostgreSQL, JWT-авторизация, REST API и WebSocket-протокол для связи с устройством.

Главное достоинство проекта - понятная архитектура и полный пользовательский сценарий: игрок регистрируется, получает код, вводит его на устройстве, проходит игру, а результаты сохраняются и доступны через API. Серверная часть не только принимает данные от устройства, но и проверяет корректность результата, считает статистику и управляет игровым процессом.

В дальнейшем проект можно развивать в сторону полноценного продукта: добавить frontend, расширить игровые режимы, повысить безопасность, улучшить аналитику и подготовить устройство к более удобной эксплуатации. Уже в текущем виде система демонстрирует основные принципы IoT-разработки и может использоваться как учебный или демонстрационный проект.
